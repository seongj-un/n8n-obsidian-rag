# RAG 오프라인 벤치 하네스

n8n 워크플로 ②(Discord 질의응답)의 파이프라인을 파이썬으로 복제한 것.
n8n 으로 한 바퀴 돌리면 ④ 기준 6분이 걸려 실험을 못 한다. 여기서는 몇 분이면 끝난다.

    맥락 재작성 → 임베딩(ollama) → pgvector 검색 → 근거 판정 → 노트 선별 → 프롬프트 조립 → 생성 → 답변 정리

마지막 동기화: **2026-09-15** (배포본 ② / ④ `updatedAt` 05:45Z 기준 — ② 는 맥락 4노드 추가분 포함).
맥락 4노드(`세션 로드` → `맥락 재작성` → … → `세션 기록` → `세션 저장`)는 **② 에만** 있다.
④ 는 단발 평가라 세션이 없고, `근거 판정`·`노트 선별` 의 `getQuestion()` 이
`["맥락 재작성", "질문 정리", "Loop Over Questions"]` 순으로 찾다가 그대로 `Loop Over Questions` 로 떨어진다.

## ⚠️ 하네스가 대변하지 **못하는** 것 — 생성 모델

**배포본의 주 답변 모델은 Gemini 다. 이 하네스는 ollama 만 부른다.**

| | ② Discord 질의응답 | ④ 답변 품질 평가 | 하네스 |
|---|---|---|---|
| 주 답변 모델 | `lmChatGoogleGemini` · `models/gemini-3.5-flash-lite` | 같음 | **없음** |
| 폴백 | `lmChatOllama` · `gemma3:4b` (`needsFallback: true`) | 없음 | `gemma3:4b` (`--model`) |

즉 `ab.py` 가 재는 생성 쪽 숫자(prefill / decode / in_tok / 답변 문장)는 **② 의 폴백 경로**이지
사용자가 실제로 받는 답변이 아니다. `ab.py` 는 실행할 때마다 이 경고를 찍는다.

### Gemini 경로를 추가하지 않은 이유

1. **키를 꺼낼 수 없고, 꺼내서도 안 된다.** n8n 크리덴셜(`Google Gemini(PaLM) Api account`)은
   암호화돼 있고 평문으로 꺼내지 않는 것이 이 저장소의 규칙이다. 하네스가 Gemini 를 부르려면
   **별도 키**가 필요하다 — 즉 "동기화"가 아니라 새 의존성을 하나 들이는 일이다.
2. **하네스의 값어치는 결정론적 계측에 있다.** `prefill_s` / `decode_s` / `in_tok` 은 ollama 가
   돌려주는 값이라 재현된다. 원격 API 는 이 분해값을 안 주고 네트워크·혼잡·쿼터가 섞인다.
   Gemini 로 바꾸면 "빠른 오프라인 실험" 이라는 존재 이유가 사라진다.
3. **정작 동기화가 필요한 부분은 모델과 무관하다.** 검색·`근거 판정`·`노트 선별`·`답변 정리`는
   전부 결정론적 코드다. 어긋나서 사고가 났던 것도 전부 이쪽이다. `parity.py` 가 이 넷을
   모델 없이 100% 검증한다.
4. **답변 품질의 진짜 점수는 ④가 준다.** 하네스의 커버리지 지표는 원래 근사치고 "방향만
   믿으라"고 적어 뒀다. 생성 품질을 Gemini 기준으로 알고 싶으면 하네스가 아니라 ④를 돌려라.
5. **검증 못 한 코드를 얹지 않는다.** 지금 이 작업에서는 모델 호출이 금지돼 있어 Gemini
   클라이언트를 붙여도 한 번도 못 돌려 본다. 그런 코드가 하네스에 들어가는 건 "어긋난 하네스"와
   같은 종류의 거짓말이다.

정말 필요해지면 `moonshot.py` 가 본보기다 — `generate()` 와 같은 모양의 dict 를 돌려주고,
키는 환경변수/`~/.<name>_key` 에서만 읽으며 절대 출력하지 않는다. 그 규약을 따라 `gemini.py` 를
새로 만들고 `ab.py --model gemini:...` 로 갈아끼우면 된다. **만들면 이 절을 같이 고칠 것.**

```python
r = urllib.request.Request("http://localhost:5678/api/v1/workflows/1MhR2JfKyXHbiTIC",
                           headers={"X-N8N-API-KEY": K})
wf = json.load(urllib.request.urlopen(r, timeout=60))
```

워크플로 ID — ② Discord 질의응답 `1MhR2JfKyXHbiTIC`, ④ 답변 품질 평가 `o2fB9QN4uRpwyaD0`.

```sh
python3 ab.py --retrieval v0 --prompt v0 --model gemma3:4b --out A.json   # 2026-09-11 이전 구성
python3 ab.py --pairs followups.json --retrieval v2 --prompt v1 --out F.json  # 후속 질문
python3 noise.py        # 질문별 best / best2mean / spread / lexHit — 임계값 재조정용
python3 leadline.py     # 형식 규칙(첫 줄 핵심 문장) 준수율
```

`ab.py` 가 찍는 prefill / decode / in_tok 은 ollama 가 돌려주는 값이라 결정론적이다.
wall 은 `docker exec psql` 오버헤드와 시스템 부하가 섞이니 비교에 쓰지 말 것.

`ab.py` 는 배포본과 같이 생성 뒤 `답변 정리`를 태운다 — `answer` 는 정리본(Discord 가 실제로
보는 것), `answer_raw` 는 모델 원출력이다. 형식 준수율처럼 원출력이 필요한 분석은 `answer_raw`
를 볼 것. **2026-09-14 이전에 만든 결과 JSON 의 `answer` 는 정리 전 원출력이다** — 섞어 비교하지 말 것.

### 후속 질문 재기 — `context.py` / `ab.py --pairs`

맥락 기능은 검색 **앞단**이다. 임베딩에 들어가는 질문 문자열 자체를 바꾸므로, 여기가
어긋나면 하류(검색·게이트·선별·프롬프트)가 통째로 다른 입력 위에서 돈다.

바뀌는 것은 **검색용 질문 하나뿐**이다. 재작성은 추측이고, 추측을 답변 프롬프트의 "질문"
자리에 넣으면 잘못 추측했을 때 사용자가 하지도 않은 질문에 답하게 된다. 검색이 틀리면
게이트가 막아주지만 답변은 막아줄 게 없다. 그래서 셋으로 나뉜다.

| 키 | 누가 읽나 | 내용 |
|---|---|---|
| `question` | 검색 · `근거 판정` · `노트 선별` | 재작성본 (`"그건 왜 비싸?"` → `"리랭킹 왜 비싸?"`) |
| `rawQuestion` | 답변 프롬프트 | 사용자 원문 |
| `contextBlock` | 답변 프롬프트 맨 앞 | 직전 차례 요약. 후속일 때만 비어 있지 않다 |

후속 판정은 **`후속 = 내용어 0개 이거나 (REF 지시대명사 있고 내용어 ≤ 1개)`**, 그리고
세션이 TTL 600초 안에 살아 있을 때만. `그럼/그러면/그래서/근데`(CONN)는 **방아쇠가 아니다** —
앞 차례를 잇기만 할 뿐 가리키지 않아서, 넣으면 `"그럼 임베딩은 뭐야?"`(주제 전환)에 직전
주제가 덧붙어 검색이 오염된다.

`--pairs` 파일은 JSON 배열이고 원소는 둘 중 하나다.

```jsonc
[
  ["리랭킹 알려줘", "그건 왜 비싸?"],          // 대화 — 차례를 순서대로 실제로 돌리고,
                                            // 앞 차례의 진짜 답변에서 answer_lead 를 뽑아
                                            // 다음 차례의 prev 로 넘긴다(배포 `세션 기록` 과 같다)
  {"question": "그건 왜 비싸?",               // prev 를 직접 주는 단일 차례 —
   "prev": {"question": "리랭킹 알려줘",       // 앞 차례를 안 돌리니 모델 호출이 절반이고
            "answer_lead": "리랭킹은 …",       // TTL 경계를 age_s 로 딱 집을 수 있다
            "topic": "리랭킹", "age_s": 5}}
]
```

결과 JSON 의 각 기록에 `raw_question` · `follow_up` · `ctx_topic` · `prev_question` · `conv` ·
`turn` 이 붙는다. `--pairs` 를 **안 주면** 예전과 똑같이 데이터테이블의 단발 질문을 돌린다 —
그때는 `prev` 가 없어 재작성이 한 글자도 일어나지 않으므로 기존 결과와 그대로 비교할 수 있다.

> `noise.py` / `leadline.py` 는 ollama 를 부르지만 `__main__` 가드가 있어 `import` 만으로는
> 모델이 돌지 않는다 — 문법 검사 때 GPU 를 먹지 않게 하려는 것이다. 새 스크립트를 넣을 때도
> 같은 규약을 지킬 것. **`ab.py` 에는 가드가 없다 — `import ab` 만 해도 전체가 돈다.**
> 문법만 볼 때는 `python3 -c "import ast; ast.parse(open('x.py').read())"`.
> `context.py` / `parity.py` / `tidy.py` 는 애초에 모델을 안 부른다.

- `근거 판정`과 `노트 선별`의 JS 는 ② 와 ④ 가 **바이트 단위로 동일**하다(`parity.py` 가 매번 확인).

- ④ 에는 `답변 정리` 가 없다 — 정리는 Discord 로 나가는 ② 에서만 한다.
- ④ Answer 에는 폴백 모델이 없다. Gemini 가 죽으면 그 실행은 실패한다.

### 게이트 규칙 (4세대 — 2026-09-15)

    grounded = best2mean < NEAR
            || (best2mean < FAR  && spread > FALL)
            || (best2mean < FAR2 && lexHit >= LEX)      ← 새 어휘 절

`best2mean` = 거리 창 안 1·2위 거리의 평균, `spread` = 창의 마지막 거리 − 1위 거리.
**거리 창(`WINDOW`=8)과 어휘 창(`LEX_WINDOW`=6)은 서로 다르다.** 거리 창은 `topK` 와 별개로
8에 못박혀 있다 — `topK` 를 16으로 넓혀도 보정이 안 깨지게 한 것이다. `topK` 를 8 **밑으로**
줄이면 임계값을 다시 재야 한다.

1·2세대는 "1위가 얼마나 독보적인가"(`best/mean8`, `best/1위노트제외최소`)를 근거의 증거로
삼았고 둘 다 같은 이유로 실패했다 — 답이 두 노트에 걸친 비교형 질문은 1·2위가 동률이라 지표가
나빠진다. 3세대는 대비를 버리고 낙폭을 본다.
4세대는 거기에 **직교하는 축**을 하나 더했다: 거리 특징 셋(best/best2mean/spread)은 전부 같은
거리 공간에서 나와 서로 상관이 높아(|r| 0.4~0.6) 임계값을 어떻게 굴려도 OUT 분포 안쪽에 박힌
IN 을 못 꺼낸다. 그래서 **"질문의 내용어가 회수된 청크에 문자 그대로 나오는가"**(`lexHit`)를 본다.

`lexHit` 계산에는 형태소 분석기 없이 도는 한국어 휴리스틱 토크나이저가 딸려 있다 —
조사/어미 꼬리(`TAILS`)를 **1회만** 떼고, 질문 골격어(`STOP`)를 버리고, 남은 내용어가 창 안
청크의 **본문 또는 노트 경로**에 그대로 나오는 비율을 센다. 영문·숫자는 단어 경계로 본다
(`m2` 가 `m20` 에 안 걸리게). 목록과 상수는 `rag.py` 상단에 배포 JS 그대로 옮겨 뒀다.

임계값을 손대기 전에 `rag.py` 의 **[한계]** 주석을 읽을 것. 요약: `LEX` 의 실제 여유는
"토큰 1개"이고(0.75~1.00 이 전부 같은 규칙), `FAR2` 는 측정된 값이 아니며, 음차 매핑
(도커↔docker)을 추가하면 그 순간 샌다.

게이트는 배포본에서 `$json.question` 을 못 받는다 — 바로 앞이 집계 노드(`Build Context` /
`Pack Docs`)라 질문이 안 흘러온다. 그래서 상류(`질문 정리` / `Loop Over Questions`)에서
직접 가져온다. **하네스는 질문을 인자로 받는다**: `ground_check(docs, question)`.
질문을 안 주면 `lexHit` 이 0 이 되어 3세대와 똑같이 동작한다(어휘 절만 꺼진다).

### 노트 선별 규칙

노트를 best 거리로 줄 세워 1위는 무조건 담고, 2·3위는 `best_i <= best_1 * band` 일 때만 담는다
(예산 `MAX_CTX_CHARS` 초과 시 중단, 단 1위 노트는 예산을 넘겨도 들어간다). 담은 노트의 청크는
`metadata.loc.lines.from` 순으로 원문 순서를 복원하고, 옵시디언 위키링크(`[[...]]`)를 걷어낸다.

**2026-09-15부터 `band` 가 질문에 따라 갈린다.** 비교 신호 정규식 `CMP` 에 걸리면 `BAND_CMP`
(1.28), 아니면 `BAND`(1.08). 비교형은 두 주제가 서로 다른 노트에 있고 질문 임베딩이 한쪽으로
쏠려서 2위 노트가 1위의 1.09~1.34배로 밀린다 — 1.08 로는 구조적으로 못 집는다. `BAND` 를
전체적으로 올리는 대신 비교형에만 올린 이유는 같은 회수율(27/28)에서 노이즈가 35% 적기
때문이다. 표와 경계값 근거는 `retrieve_v2.py` 상단 주석에 있다.

`MAX_CTX_CHARS` 도 8500 → 11000 으로 함께 올렸다. 8500 에서는 `BAND` 를 1.40 까지 올려도
26/28 이 천장이다(카프카 문항이 9,643자를 요구한다).

선별 노드도 질문이 필요하다: `select(probe, question)` / `select_full(probe, question)`.
안 주면 비교형 판정이 꺼져 `BAND` 1.08 로 동작한다 — 배포본이 질문을 못 구했을 때와 같은 폴백이다.

### 답변 정리 (② 전용)

내용은 한 글자도 바꾸지 않는다. ①출처 표기 제거 → ②뭉친 불릿을 제 줄로 → ③리드 문장 복구 →
④라벨 없는 불릿 머리 굵게 → ⑤**빈 줄 정규화**.

**2026-09-15부터 ⑤가 바뀌었다.** 예전에는 빈 줄을 전부 버리고 블록(본문/목록) 사이에만 다시
넣었다. `Answer` 의 SYSTEM 이 질문 종류별 모양으로 바뀌자 이 방식이 의도한 문단을 뭉갰다 —
비교형의 대조 줄 묶음과 번호 목록(1. 2. 3.)이 산문 문단과 한 덩어리로 붙어 나왔다. 이제는
모델이 넣은 빈 줄을 **살리고**, 연속된 것만 하나로 줄이고, 본문 뒤에 목록이 시작될 때만 한 줄
띄운다. 구조상 멱등이다.

### `Answer` 의 SYSTEM (2026-09-15 개정)

질문 종류를 보고 **셋 중에서 모양을 고르게** 한다 — (가) 비교는 대조 줄, (나) 동작·절차는 번호
목록, (다) 정의·개념은 산문 두세 문장 + 불릿 3~5개. 예시도 셋이다. 이전에는 "리드 문장 +
불릿 5~8개" 하나만 시켜서 비교형까지 불릿 나열이 됐다.
문자열 전체는 `prompt_v1.py` 의 `SYSTEM` 에 배포본 그대로 들어 있다(1281자, ②·④ 동일).

### ④ 는 2패스 구조 (2026-09-15)

```
Loop Over Questions ─(each)→ Retrieve → Pack Docs → 근거 판정 → 근거 있나?
                                                       ├─true→ 노트 선별 → Answer ┐
                                                       └─false→ 답변(거절문) ─────┤
                                                                     답변 저장 ←──┘  (staticData 에 쌓기)
Loop 종료 ─→ 채점 준비 → 채점 루프 ─(each)→ Judge → Record → Build Report → Discord
```

문항마다 답변/채점 모델을 번갈아 부르면 27문항에 모델을 54번 재적재하게 된다(실측: 채점
1회 91초 중 83초가 교체 비용). 그래서 **패스1에서 답변만 전부 만들어 `staticData` 에 쌓고,
패스2에서 채점을 몰아서** 한다.

채점 모델은 `qwen3:4b` + `format: json` + `think: false`. `format: json` 이 켜져 있으면 n8n
체인이 JSON 을 미리 파싱해 `$json.text` 가 아예 없다 — `Record` 가 두 모양을 모두 읽는다.
거절 문항의 채점은 모델에 맡기지 않고 `Record` 가 코드로 판정한다(음성 대조군의 올바른
거절 = 5/5/5, 그 외 거절 = 0/0/0).

이 2패스·채점 로직은 **하네스에 사본이 없다.** ④ 는 평가 워크플로지 답변 파이프라인이 아니고,
하네스가 복제하는 것은 ② 의 파이프라인이기 때문이다. `근거 판정`·`노트 선별`·`Answer` SYSTEM
은 ②와 동일하므로 하네스가 그대로 대변한다.
